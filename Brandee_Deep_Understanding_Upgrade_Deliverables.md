# Brandee Deep-Understanding Pipeline Upgrade — Deliverables Report

This report covers a full rebuild of Brandee's website crawler, business-profile extraction, recommendation engine, hook selection, copywriting, storyboard generation, and results page, done directly in the AIStaff codebase. Every item below was inspected, reproduced, implemented, and validated — not just recommended. All fixtures used in automated tests are fictional (a made-up "Sample Rentals Co." / "BrightDesk Solutions" style business); no real client data, including Marga Enterprises or marga.biz, was used as test input or expected output anywhere in this work.

## 1. Root causes found in the previous implementation

Before rebuilding, the previous single-page heuristic extractor and planner were inspected directly (not assumed) to confirm each failure mode named in the brief actually existed in code:

The business name was read straight from `<title>`, with no fallback hierarchy and no rejection of generic SEO-keyword titles ("Best Consulting Services in Town"). Generic headings such as "Conclusion" or "Related Posts" were filtered out of `productsOrServices` by a small stoplist, but the *same filtered array* was reused verbatim for `primaryBenefits` — so a product name and a benefit were always identical strings pulled from the same list, with no real separation between what a business sells and why it matters. Contact extraction only ever ran a regex over the homepage's visible text looking for an email pattern and a PH mobile-number pattern; it never read `tel:`/`mailto:` hrefs and never visited a dedicated Contact page, so real contact methods were routinely missed. Hook scoring used a flat per-category "curiosity" constant and mostly binary values for the other dimensions, so two different hooks in the same category (e.g. two different curiosity hooks) always converged on nearly identical scores regardless of how well each was actually filled in — this was reproduced directly: h001 and h007 scored the same under the old logic. The "years in business / expertise" proof gate was satisfied by *any* differentiator being present, which let personal-experience hook templates like "What I learned from failing at {{activity}} 10 times" get approved off the back of an unrelated differentiator, fabricating a personal narrative with no supporting fact. Alternative "angles" were frequently the same problem/outcome pair reworded across hook categories, not materially different creative directions. For non-English requests, `buildScript()` appended a literal authoring instruction — `" (write final dialogue in natural Taglish, not stiff translated English)"` — directly into the customer-facing caption string, so customers could see an internal instruction that was never actually executed by anything. Raw user form input such as `"business owner, companies"` was substituted unnormalized into hook templates, producing visibly broken comma-fragment copy.

## 2. Crawler architecture: before vs. after

Before: a single `safeFetchHtml()` call against the homepage only, followed by regex extraction over that one page's visible text. No navigation, footer, or sitemap discovery; no subdomain awareness; no page classification.

After: `src/brandee/crawler.js` implements a bounded, injectable-dependency, breadth-first crawler (`discoverAndCrawl()`) that discovers links from the homepage's nav/footer/body, `sitemap.xml` (via `robots.txt` and common sitemap paths), scores and prioritizes candidate URLs before visiting them, and crawls up to a configurable page/depth budget. Every network call goes through `fetchHtmlPage`/`fetchTextResource` parameters that default to the real SSRF-safe fetchers in `websiteAnalyzer.js` but can be swapped for fakes in tests, so the crawler's logic is fully testable without any real network access.

## 3. Link discovery method

`parseHtmlDocument()` in `crawler.js` extracts every `<a>` href from the page along with its surrounding context (nav, footer, or body) and anchor text. Each discovered link is normalized and deduplicated (tracking parameters, fragments, and session IDs stripped) before being queued, so the same page reached via different query strings or link text is only crawled once.

## 4. Menu, footer, and sitemap parsing

The parser separately tags `navigationText` and `footerText` blocks apart from `mainText`, so evidence extracted from a nav/footer element (e.g. a logo alt attribute or a copyright line) is distinguishable from body content. `discoverSitemapUrls()` fetches `robots.txt` first to find any declared `Sitemap:` entries, then falls back to `/sitemap.xml`, `/sitemap_index.xml`, and `/sitemap-index.xml`, parsing `<loc>` entries out of the XML with a dependency-free regex parser (consistent with the rest of this codebase's no-HTML-parser-library approach).

## 5. Page classification before visiting

`src/brandee/pageClassifier.js`'s `classifyPageType()` assigns a type (homepage, about, contact, product, product_category, service, service_category, pricing, plans, offers, faq, testimonial, case_study, portfolio, booking, location, terms, privacy, blog_index, blog_article, or unknown) using URL-pattern rules first (most reliable, language-independent), then schema.org type, then title/heading text — never guessing "product" or "offer" from a bare homepage heading. `isNonContentHeading()` rejects "Conclusion", "Summary", "Related Posts", "Learn More", "Table of Contents" and similar section labels from ever being treated as a product, benefit, or proof point. `scoreLinkCandidate()` in `crawler.js` uses this classification, plus nav/footer prominence and anchor/URL relevance, to prioritize product/service/pricing/about/contact/FAQ/testimonial pages and deprioritize privacy/terms/login/pagination/tracking pages in the crawl queue.

## 6. Crawl limits (env-configurable)

`getCrawlConfig()` in `crawler.js` reads: `BRANDEE_CRAWL_MAX_PAGES` (default 20), `BRANDEE_CRAWL_MAX_DEPTH` (default 3), `BRANDEE_CRAWL_TIMEOUT_MS` (default 8000), `BRANDEE_CRAWL_MAX_RESPONSE_BYTES` (default 1,500,000), `BRANDEE_CRAWL_ALLOW_SUBDOMAINS` (default true), and `BRANDEE_CRAWL_MAX_SUBDOMAINS` (default 3). Every one of these is read fresh from `process.env` at call time (not baked in at module load), so an operator can tune crawl behavior per deployment without a code change.

## 7. Subdomain and external-link rules

`classifySourceType()` in `src/brandee/urlUtils.js` labels every discovered URL as `same_domain`, `linked_subdomain`, or `linked_external` relative to the submitted root domain. The crawler only follows a subdomain if it was *actually discovered as a link* on an already-crawled page — it never guesses common prefixes like `portal.`, `app.`, `shop.`, `customer.`, or `client.`. External domains are recorded as evidence (e.g. a Facebook/Instagram link found in a footer) but are never themselves crawled. This directly enforces the brief's constraint against assuming a customer portal exists on an undiscoverable subdomain.

## 8. Business-name resolution

`src/brandee/businessNameResolver.js`'s `resolveBusinessName()` uses a weighted evidence hierarchy: schema.org Organization/LocalBusiness name (weight 1.0) > Open Graph `site_name` (0.9) > logo `alt` text (0.85) > footer copyright line (0.8) > About/Contact page heading (0.55) > homepage title's first segment (0.35) > homepage H1 (0.3) > domain name, titleized (0.15). `isGenericName()` rejects "Home", "Products", "Services", "Contact", SEO-keyword openers ("best", "top", "#1", "leading", "trusted"), long sentence-like strings, and names starting with a digit. Cross-page repetition of the same name gives a small confidence boost; a close runner-up candidate triggers an ambiguity penalty rather than false confidence.

## 9. Product/service discovery

`src/brandee/entityExtraction.js`'s `extractProductsAndServices()` only pulls candidates from pages classified as `product`, `product_category`, `service`, or `service_category` (falling back to the homepage only when no such page was found at all). A dedicated single-item page's own title is a valid name candidate; a *category/listing* page's title is deliberately excluded from that role, since it is normally a generic label for the whole category ("Services", "Shop") rather than one specific offering — this exact bug (a category page's own title being captured as if it were a product) was caught and fixed during this task's own integration testing, described in section 30 below. Items with the same normalized name found on multiple pages are consolidated into a single entry with all source URLs and evidence attached.

## 10. Contact extraction

`extractContacts()` reads every crawled page's `tel:`/`mailto:` hrefs plus Messenger, WhatsApp, Viber, booking-link (Calendly/Cal.com/Acuity/Booksy/Setmore), Facebook, and Instagram href patterns from that page's calls-to-action — across *all* crawled pages, not only the homepage. Visiting an actual classified Contact page is itself recorded as `contact_form` evidence.

## 11. Blog detection

`detectBlogState()` returns one of `blog_present`, `blog_empty`, `blog_link_present_but_no_articles`, `blog_not_found`, `blog_unreachable`, or `unknown`. `blog_present` is only returned when actual `blog_article`-classified pages were crawled; a nav link to `/blog` with no articles found yields `blog_link_present_but_no_articles`, never a fabricated claim that content exists.

## 12. Evidence classification (verified / user-supplied / inferred)

`src/brandee/evidenceModel.js` defines the `Evidence` shape (`statement, sourceType, sourceUrl, excerpt, confidence, entityType`) with `sourceType` restricted to `website`, `linked_subdomain`, `linked_external`, `user`, or `inference`. `isVerified()`, `isUserSupplied()`, and `isInferred()` helpers, plus `partitionEvidence()`, are used throughout the pipeline (and in the results-page renderer) so inferred content is never displayed as if it were a verified website claim.

## 13. Feature / benefit / business-outcome separation

`extractFeaturesAndBenefits()` classifies each heading as a `feature` (a concrete capability) or a `functional_benefit` (a stated improvement, detected via a benefit-verb pattern such as "save," "reduce," "faster," "easier") using surface language only. `deriveBusinessOutcomes()` builds a third, distinct layer from those — and always tags its output `sourceType: "inference"`, so a business outcome (a higher-level claim like "helps you grow") is never presented as a directly verified website statement, only as a reasoned inference from verified features/benefits.

## 14. Upgraded BusinessProfile schema + orchestrator

`src/brandee/schemas.js`'s `WebsiteBusinessAnalysisSchema` (aliased as `BusinessProfileSchema`) was rewritten to the full shape specified in the brief: `crawlSummary`, `sourceMode`, `businessName`/`businessNameConfidence`, structured `productsOrServices[]` (with features/functionalBenefits/businessOutcomes/customerProblemsSolved/idealCustomers/evidence/confidence per item), `customerProblems[]`, `customerDesires[]`, `features[]`, `functionalBenefits[]`, `businessOutcomes[]`, `differentiators[]`, `offers[]`, structured `contactMethods[]` (`ExtractedContact[]`), `proof{}` (verified-number objects, not raw numbers), `evidence[]`, `inferences[]`, `missingInformation[]`, `contradictions[]`, and `confidence`. `src/brandee/businessProfileBuilder.js` is the new orchestrator that runs the crawler, name resolver, and every entity extractor and assembles this object; it lives as its own module (rather than inside `websiteAnalyzer.js`) specifically to avoid a circular require, since the crawler itself depends on `websiteAnalyzer.js` for SSRF-safe fetching.

## 15. Profile-confirmation flow

`buildBusinessProfile()` computes `confirmationRequired` and human-readable `confirmationReasons` (low business-name confidence, no products/services found, no contact method found, fewer than 2 pages crawled, no ideal-customer field confirmed) and an overall `confidence` score. `server.js`'s response includes a `profileConfirmation: {required, reasons}` object, and the results page (`public/agents/brandee/plan/index.html`) shows a confirmation banner and a "Discovered on your website" section so low-confidence extractions are surfaced to the customer for confirmation rather than silently assumed.

## 16. Awareness improvements (campaign context)

`src/brandee/awareness.js` now accepts an `audienceSource` (`cold_audience`, `broad_targeting`, `interest_targeting`, `lookalike`, `engaged_audience`, `website_visitors`, `previous_leads`, `abandoned_inquiry`, `existing_customers`, or `unknown`). Each known source maps to a plausible awareness-level *range*; the existing content-based heuristic (`classifyFromContent`) picks or refines within that range rather than being allowed to claim a level the audience source rules out — a `cold_audience` can never be classified `most_aware` no matter how much proof the website has, and `existing_customers` can never be classified below `most_aware` even on a bare website. When `audienceSource` is `unknown`, behavior falls back exactly to the old content-only heuristic, with confidence explicitly capped at 0.55 and an uncertainty note appended to the explanation.

## 17. Angle-diversity engine

`src/brandee/angleDiversity.js`'s `buildDistinctAngles()` builds each `CreativeAngle` (`id, name, customerProblem, desiredOutcome, coreMessage, reasonToBelieve[], proofUsed[], formatSuitability[], awarenessFit[], goalFit[]`) from real problem/outcome/differentiator pools extracted from the business profile, round-robining across distinct pool entries instead of reusing the same one for every angle. `angleSimilarity()` computes token-overlap similarity across problem+outcome+message; any candidate angle scoring ≥0.6 similarity to an already-accepted angle is rejected and retried against a different pool entry (up to the number of available candidates) before being accepted anyway with a recorded `similarityWarnings` entry, so paraphrased near-duplicates are caught rather than silently presented as three "different" angles.

## 18. Independent hook scoring + hard safety gates

`src/brandee/hookScoring.js`'s `scoreHookIndependently()` computes 11 independent dimensions per hook (relevance, clarity, specificity, curiosity, credibility, audienceFit, platformFit, goalAlignment, proofSafety, naturalness, distinctiveness) from the hook's actual filled-in text and context — not a flat per-category constant — so two hooks in the same category now reliably score differently based on how well each is actually written. The total is always recomputed in code from the individual scores (`Object.values(scores).reduce(...)`), never trusted from any upstream source. Hard safety gates independently override the numeric total: `detectPersonalExperienceClaim()` + a specific `hasVerifiedYearsInBusiness` check (not the broader category-level proof bucket) blocks fabricated personal-failure-count narratives unless that specific fact is actually verified; `detectAbsoluteClaim()` blocks "only... ever need" / "everyone" style unsupported absolutes regardless of any other proof present; `detectUnsupportedUrgency()` blocks fabricated scarcity language without a verified deadline. Rejected hooks are retained internally (`rejectedHookScores`) for diagnostics only — never shown to the customer.

## 19. Framework alignment validation

`src/brandee/decisionEngine.js`'s `validateFrameworkAlignment()` checks that a chosen static-ad framework's headline actually earns that framework: Question requires a headline genuinely phrased as a question; Testimonial requires at least one verified testimonial; Offer requires a real, verified offer; Before-and-After requires an actual describable problem/transformation; Us vs. Them requires at least one verifiable differentiator; Bold Claim rejects headlines containing unsupported absolute language ("guaranteed," "100%," "never fails," "always works"). `buildStaticAdConcept()` in `planner.js` loops through framework candidates and picks the first one that both fits the decision constraints and passes this alignment check, rather than forcing a misaligned framework through.

## 20. Copy-editing / quality validation

`src/brandee/copyQuality.js` provides `normalizeRawPhrase()` (turns raw comma fragments like `"business owner, companies"` into `"business owners and companies"` before any template substitution happens), `detectGrammarIssues()` (duplicated words, repeated punctuation, unresolved `[placeholder]` markers, and — directly targeting the verified leak bug — authoring-instruction phrases like "write final dialogue," "insert proof here," "rewrite in natural Taglish"), `hasPlaceholderLeak()`, and `validatePlanCopyQuality(plan)`, which scans every customer-facing copy field in a generated plan (primary hook, alternative hooks, every scene's dialogue/caption, static-ad headline/supporting copy) and returns a list of concrete failures. `generateCreativePlan()` in `planner.js` runs this check as part of its retry-or-throw gate — a plan that fails copy quality after one rebuild attempt throws the typed `BRANDEE_COPY_QUALITY_FAILED` error rather than shipping.

## 21. UGC script / storyboard improvements

`src/brandee/ugcScript.js`'s `buildUgcScenes()` produces the 5-scene structure (hook, problem, solution, benefit/proof, call-to-action), each scene carrying `purposeCategory`, `onScreenText`, `productDirection`, `evidenceUsed`, and `estimatedWordCount`. The hook is never repeated verbatim as a later scene's dialogue, and no scene invents a personal story or customer experience beyond what was actually supplied as evidence. `validateScenes()` checks each scene's estimated word count against its allotted duration using a language-specific words-per-second rate (English 2.5, Filipino 2.2, Taglish 2.3 — a genuinely slower allowance, verified in testing to actually change which scenes get flagged), and checks for placeholder/authoring-instruction leaks and grammar issues. `validateCtaAlignment()` confirms the closing scene's call-to-action language matches the selected goal's approved CTA examples. This directly replaces the previous behavior where a literal localization instruction was appended into the visible caption string for any non-English request.

## 22. Static-ad concept improvements

`buildStaticAdConcept()` in `planner.js` now produces `subheadline`, `verifiedBenefit`, `differentiator`, `layoutDirection`, `assetRequirements[]`, `proofUsed[]`, `prohibitedClaims[]`, and `aspectRatios[]` alongside the existing headline/supporting-copy fields, with framework selection validated per section 19 above rather than picked without regard to whether the business's actual proof supports it.

## 23. Results page redesign

`public/agents/brandee/plan/index.html` now renders a confirmation banner when `businessProfileConfirmationRequired` is true, a "Discovered on your website" section (products/services and contact methods actually found by the crawler, each tagged with a human-readable evidence-source label instead of a raw internal string), and a redesigned hooks section that shows only the top 3 scored hooks by default behind an expandable "Show N more scored hooks" control — rejected hooks are never rendered on the customer-facing page at all, only retained server-side for diagnostics. Proof rendering now shows the evidence source (website / linked page / user-supplied / inferred) rather than an opaque internal code.

## 24. Admin crawl diagnostics

`src/admin/brandeeRunLog.js`'s `recordRun()` accepts and stores a `crawlDiagnostics` object (pages discovered/crawled/rejected, page types found, subdomains crawled, business-name confidence, products/services count, contact methods found, blog state, confirmation-required flag) without exposing any secret or private page content — the existing generic admin `runs` list route automatically surfaces this new field with no additional route changes needed.

## 25. Corey Haines marketing-skills runtime status

`src/marketingSkills/{registry,loader,manifest,skillRouter,contextBuilder,validation}.js` were added as an explicit, honestly-labeled scaffold. `loader.js`'s `loadSkillContent()` always returns `null`, and every status check reports `installed_for_development` or `runtime_inactive` — this code deliberately does **not** read from `.claude/skills` during live production requests, and does not claim to be active. It exists so a future task can wire real skill content in without inventing a false "already active" claim today.

## 30. Tests run — and two real bugs found and fixed by running them

`npm test` (`node --test test/**/*.test.js`) was run for the first time after all the new modules and rewritten schemas were in place. Result: 173 passed, 1 failed on the first run. The one failure was real: `buildHeuristicAnalysis()`'s `productsOrServices` entries were missing the now-required `id` and `type` fields after the `ProductOrServiceSchema` rewrite — fixed in `websiteAnalyzer.js` by generating a stable `id` and defaulting `type: "service"` for that single-page fallback path (which cannot reliably distinguish product vs. service without a full crawl). Re-run: 174/174 passed (3 pre-existing, environment-only skips in the admin test suite for "no reachable database in this sandbox," unrelated to this task).

Beyond the unit suite, a full end-to-end integration smoke test was built and run directly (fictional in-memory five-page site → `buildBusinessProfile()` → `generateCreativePlan()` → schema validation of both outputs), since the unit tests exercise each module in isolation but not the full wired-together pipeline. This surfaced a second real bug that no individual unit test had caught: a category/listing page's own `<title>` (e.g. "Services — Sample Rentals Co" on a `/services` listing page) was being captured as if it were itself a specific product/service name, alongside the real sub-headings on that page ("Desk Equipment Rental," "Equipment Maintenance") — exactly the kind of "generic heading treated as a product" failure the brief explicitly warned against, just one level higher (a whole category page rather than a single heading). Fixed in `entityExtraction.js`'s `extractProductsAndServices()`: the page's own title is now only used as a name candidate on a genuinely single-item page (`pageType === "product"` or `"service"`), never on a category/listing page (`"product_category"`/`"service_category"`), with `isNonContentHeading()` applied as an additional safety net. Re-ran the smoke test and the full suite afterward — both clean.

A second integration smoke test covering the "website completely unreachable" path (`fetchStatus: "unreachable"`, `sourceMode: "manual_only"`) was also run end-to-end through plan generation, confirming the manual-only fallback still produces a schema-valid `BusinessProfile` and a schema-valid plan with `businessProfileConfirmationRequired: true`, and that the optional AI-enhancement pass no-ops gracefully with no API keys configured in this sandbox rather than crashing.

## 31. Build result

`node --check` was run against every new and modified source file (all `src/brandee/*.js`, all `src/marketingSkills/*.js`, `src/server.js`, `src/admin/brandeeRunLog.js`, `src/admin/routes.js`) — zero syntax errors. A separate require-graph check loaded every one of the 26 Brandee/marketingSkills modules directly in Node with no errors (confirming no circular-require breakage, which was a known risk given `businessProfileBuilder.js` depends on both `crawler.js` and `websiteAnalyzer.js`). `node src/server.js` was booted directly in this sandbox: it registered its routes and began listening on port 3000 successfully; the only error that surfaced afterward was a Prisma "Query Engine binary mismatch" (the Prisma client here was generated for macOS/`darwin-arm64`, but this sandbox is Linux) — an artifact of running this Linux sandbox against a client built for the real Mac deployment target, not a bug in this task's changes, and it was caught and kept non-fatal by the existing global process safety net from a previous hardening task rather than crashing the server.

## 32. Remaining limitations

The optional AI-enhancement pass (`enhancePlanWithAi`, `enrichBusinessAnalysisWithAi`) was exercised only in its no-provider-configured, graceful-no-op form in this sandbox — it was not exercised against a live OpenAI/Gemini call, since no API keys are available here; this remains the single largest untested path and should be checked on the real deployment where those keys are configured. The angle-diversity retry logic accepts a similar angle anyway (flagged via `similarityWarnings`) once it exhausts its retry budget on a business profile with very few distinct problems/outcomes — for a business with only one real problem to solve, three *fully* distinct angles may not be achievable, and this is surfaced honestly rather than silently forced. The crawler's link-scoring and page-budget logic have not been tested against a real, large, unpredictable production website — only against small fictional in-memory fixtures — so real-world sites with unusual navigation structures, JavaScript-rendered menus (this crawler, like the rest of this codebase, does not execute JavaScript), or very large sitemaps are the primary remaining unknown. Finally, this report's "build result" is a sandbox verification (syntax, require-graph, and boot-to-listening); it is not a substitute for the live-testing steps below on the actual PM2/Cloudflare Tunnel production host.

## 33. Exact steps for testing this on a real client website

On the machine that actually hosts Brandee (PM2 + Cloudflare Tunnel, not DigitalOcean), pull these changes, run `npm install` if any dependency changed (none did in this task), then `npm test` to confirm the full 184-test suite still passes in that environment. Restart the live process the same way it was restarted earlier in this engagement (`npm run start:live`, or the equivalent PM2 reload command already in use), and confirm `npm run status:live` reports the process healthy. Then, from the normal customer-facing interface (not a special internal route), submit the Brandee analyze form with a real website URL, a real "what you sell" description, and a real "ideal customer" description — the same way any customer would. Confirm the resulting plan-results page shows a "Discovered on your website" section whose products/services and contact methods genuinely match what is on that real site, confirm the confirmation banner appears if and only if Brandee's own confidence is genuinely low, confirm no rejected hooks are visible anywhere on the page, and confirm the final UGC script and static-ad concept contain no bracketed placeholders, no authoring instructions, and no claims (proof, urgency, authority) that aren't either on the real site or entered manually in the form. No special-cased logic exists anywhere in this implementation for any particular business, so this test is representative of what any other customer's submission would produce.
